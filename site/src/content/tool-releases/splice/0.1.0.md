The first version of splice: a batch of exact edits to files, all checked before anything is written.

## Made for coding agents

AI coding agents often edit files with a few lines of inline Python, because it lets them make several replacements in several files in one command. In a month of agent transcripts (2026-10-14 to 2026-11-13), they did that 6,294 times, against 2,336 times with their own editing tool, which takes one replacement at a time. It works until a check is forgotten, a mismatch says only `AssertionError`, or a failure halfway leaves half the files written. splice keeps the batch and fixes those.

## What is in it

- **Edits as SEARCH/REPLACE blocks**, a format many models already know: a header line that names the file, then the old text and the new text between marker lines. splice reads them from standard input or from files. In a shell, a quoted heredoc keeps the text exactly as written:

  ```sh
  splice <<'EOF'
  src/server.go:Server.run
  <<<<<<< SEARCH
  	log.Printf("start")
  =======
  	log.Printf("start %s", s.addr)
  >>>>>>> REPLACE
  EOF
  ```

- **All or nothing.** splice applies every block in memory first. If one fails, it writes nothing, reports every block that failed, and says whether the others would apply. The changed files are written to temporary files next to them and renamed into place only when all of them are written, so a read-only file or a file that changed on disk meanwhile stops the whole batch.
- **A mismatch says where.** Old text that isn't there gets the nearest lines and the first one that differs, with tabs shown as `→` and spaces at the end of a line as `·`. Old text that is there more than once gets every place, with the function it is in. When the new text is there already, splice asks whether the block was applied before.
- **Exactly once, or every time.** The old text has to be there exactly once (overlapping occurrences count), or `SEARCH all` replaces each one. When the text isn't there as written, splice tries again without the spaces at the ends of lines, then with the indentation shifted, and the report says so.
- **Headers that narrow the search.** A header can be a file, a definition (`src/server.go:Server.run`), a line inside one (`main.go:104`), or a range of lines (`main.go:80-120`): the forms the other tools of the family print. A file can be named by the unique end of its path (`pty.rs`).
- **Whole definitions, new files, deleted lines.** Empty old text under a header that names a definition replaces the whole definition and keeps its doc comment. Empty old text under a file that doesn't exist creates it, with its folders. No new text deletes the old text.
- **A report by definition.** One line per changed function, type or section, such as `changed func Server.run L40-71 (+1 -1)`, so the file and the name join into a place the other tools take. A changed signature gets a `next:` line with the seek command that lists its callers. A Go or JSON file that could be read before the edit and can't after it gets a `check:` line with the place of the error.
- **Files stay what they were.** Modes are kept (setuid and setgid too), a symlink stays a symlink, a file with several hard links keeps them all, and in a file with mixed line endings, a line that ended in `\r\n` still does.
- **`-n`** checks and reports without writing anything, and **`--diff`** also prints each block's old and new lines.

The exit code is 0 when every block applied, 1 when one failed and nothing was written, and 2 for input splice can't read. Three reviews and their re-checks went through it before this tag, and each problem they found has a test of its own.

## Underneath

Built on Prism 0.9.0, the parser the tools of the family share. It finds the definitions a header names and the report lists. The report finds the definition of every changed line in one pass: about a second for 120,000 functions.
