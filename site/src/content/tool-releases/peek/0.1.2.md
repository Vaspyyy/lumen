title: Errors in sentences, not in file names
summary: A line like "Deploy failed." counts as an error and an error name inside a file name doesn't, jq's output is read as records, and Python's logs are read as logs.
---

## Fixed

- **A failure at the end of a sentence is an error.** `Deploy failed.`, `Found 2 errors.` and `status=1/FAILURE` weren't counted in 0.1.0 and 0.1.1. Neither was a `level=` field that holds no level name, as in `connection failed (retry level=max)`: it hid the failure in front of it.
- **An error name inside a file or class name is not.** `Compiling ValidationError.swift` and a Java stack line such as `at com.x.ValidationException.<init>(…)` were counted as errors. A name with a message after it still is: `IOException: disk full`.
- **After a place in a file, a level word decides.** `x.py:3: DeprecationWarning: old` is a warning. A `path:line: message` line without a level goes by its words, so `README.md:3: trailing whitespace` is no longer an error.
- **`Caused by:`**, the line where Java names the cause of an error, is an error.
- **Several JSON values one after another**, as `jq` prints them, are read as records. They came out as JSON Lines with no records.
- **Python's logs are logs.** Their times have a comma in them (`10:00:00,123`), and peek read such a log as a CSV file. A rotated log such as `app.log.1` is text too.
- **Past 200 different strings at one path, only sure repeats are shown**: `over 200 distinct, repeated at least: "hot" ×500`. The estimate before could show a string as frequent that wasn't.
- **An object of records can have `null` values** and still be read as a map.
- **Empty standard input with a path** says that nothing came on stdin.
