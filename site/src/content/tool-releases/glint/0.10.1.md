title: No hang on named pipes
summary: glint no longer waits forever when a folder holds a named pipe under the name of a manifest or a source file. It reads regular files only, in every view.
---

## Fixed

- **No hang on named pipes.** A named pipe is a special file that one program writes into and another reads from. Opening one to read waits until something writes to it, and a pipe can have any name. `glint -A`, `-C` and `-P` never came back in a folder with a pipe called `go.mod` or another manifest, `glint -A` never came back with a pipe called `main.go` next to another source file, and `glint -p` never came back on a link to a pipe: 164 of 1,026 test runs were still waiting after four seconds. glint now reads regular files only, and opens them and the folders it lists without waiting. That holds for every view, the interactive one included, and also when a path is swapped for a pipe while glint runs.
- **A config file in its usual place that isn't a file** (a pipe, a device, a link to `/dev/null`) counts as no config. A file named with `--config` is read as given, so `--config <(…)` works.
- **`ffprobe` gets three seconds per file**, and so does whatever it starts.
- **Line counts are read in chunks**, up to a gigabyte for one file. A file that holds more than its size says (one in `/proc`, or one that grew) gets a count instead of `0L`.

Not covered: git itself waits on a pipe in the place of one of its own files, such as `.gitignore` or `.gitattributes`, and glint waits with it.

## Underneath

- Built on Prism 0.9.0: an outline's ranges end where the definitions do when a type or a value has a `{` or a `;` in it (`fn f() -> [i32; 3] {`, `func f() interface{} {`, `function f(): { ok: boolean } {`), and Kotlin's `enum class`, `fun interface`, `inner class` and `operator fun` have their names.
