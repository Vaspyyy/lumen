The first version of recap: a git diff that tells you what happened to the code, not just which lines differ.

## What is in it

- **A change, told by symbol.** A symbol is a named piece of code: a function, a type, a class, a heading in Markdown. recap reads a git diff and lists, under each changed file, the symbols that were changed, added, removed, renamed or moved, with their line ranges. Small changes show their changed lines right there.
- **Signatures that changed** are shown as `was:` and `now:` lines, also when they are spread over several lines. `(public)` marks a change to what other code can use, such as an exported Go name or `pub` in Rust. A new trait method without a default is marked as one every implementation has to add.
- **Code that moves is followed**: from one file to another, out of a function into a new helper, and into files git sees as deleted and new. recap says whether the code changed on the way and shows the lines that differ, which is where a change hidden in a refactor usually sits.
- **`recap --show file:name`** prints the diff of one symbol, so you read the few changes that matter and skip the rest.
- **The same arguments as `git diff`**: `recap` for the working tree with new files, `recap --staged`, `recap HEAD~3`, `recap v1.2 v1.3`, `recap main...feature`. `recap show` describes one commit with its message, `recap log -n 5` the last five commits. Paths after `--` limit any of them.
- **Labels for changes that change nothing**: whitespace only, a doc comment only, decorators only, line endings only.
- **A size it keeps to.** The overview uses about 150 lines (`-b N` sets another number). When it has to cut, every file keeps its line, signature changes, renames and removals come first, and what is left out is counted by kind. `-p` prints git's full diff after the overview.

## Made for coding agents

recap was written for AI coding agents, which pay for every line they read. When its output is not a terminal it prints plain text without colors (`-A` asks for that anywhere). On the real history of three projects, its output came to about 3% of the text of the same `git diff` and `git log -p`: the last ten commits of glint were 153,980 tokens with `git log -p -n 10` and 1,803 with recap. On a small diff it saves less, because its labels and line ranges take about as much room as the diff itself.

Before release, several AI models used it on branches, commits and a refactor with a planted bug, and all of them found the bug from recap's overview.

## Good to know

- Symbols come from [glint](https://github.com/Vaspyyy/glint)'s outline rules: Go, Rust, Python, JavaScript and TypeScript, C and C++, Java, Kotlin, C#, GDScript, shell, Lua, Ruby and Markdown headings. Other files get their line counts, and their changed lines when there are only one or two.
- recap compares definitions, not behavior. It tells you that a function changed and, for small changes, which lines, but not what the change means. When the exact change matters, use `--show` or `git diff`.
